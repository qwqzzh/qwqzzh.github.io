Photo Mosaics
by hand, then automatically

Part A: photos taken while rotating about the camera's center, homographies recovered from clicked correspondences by least squares, inverse warping written from scratch, rectified signs, and four blended mosaics around the Berkeley campus. Part B: the clicking is replaced by Harris corners, ANMS, patch descriptors, ratio-test matching and 4-point RANSAC.

PROJECT MAP

Shoot

Turn the phone about its lens, so every photo sees the scene from one center of projection.

A.2

Solve

Click matching points and solve a 2n × 8 least-squares system for the homography H.

A.3

Inverse-warp with nearest-neighbor or bilinear sampling and use it to rectify planar objects.

A.4

Blend

Warp every photo into the middle photo's frame and blend the overlaps without seams or ghosts.

B.1

Find Harris corners and keep 500 well-spread ones with adaptive non-maximal suppression.

B.2

Sample a blurred, normalized 8 × 8 patch from the 40 × 40 window around each corner.

B.3

Pair similar descriptors, keeping a match only if it clearly beats the second-best candidate.

B.4

Verify

Use 4-point RANSAC to find the largest consistent set of matches, then stitch without any clicks.

PART A

Image Warping and Mosaicing

PART A · 1

Shooting the pictures

A homography can only map one photo onto another if both were taken from the same center of projection (or if the scene is a plane). So for each mosaic I stood in one spot and turned the phone about its lens between shots, leaving roughly 40–70% overlap between neighbors. I shot four sets on and around the Berkeley campus: three photos of a white campus building (set 1), two of a hall (set 2), two of a crosswalk (set 3) and three of a street with autumn trees (set 4). For rectification I photographed two rectangular signs at a steep angle. Every photo is resized so that its long side is at most 1600 px before any processing.

PART A · 2

Recovering homographies

A homography maps a point p = (x, y, 1)ᵀ of one image to p′ ∼ Hp in the other, where H is a 3 × 3 matrix defined up to scale. Fixing h33 = 1 leaves 8 unknowns. Writing out the division by the third coordinate,

x′ = (h11x + h12y + h13) / (h31x + h32y + 1),   y′ = (h21x + h22y + h23) / (h31x + h32y + 1),

and multiplying out the denominator gives two equations per correspondence that are linear in h = [h11 … h32]ᵀ:

[x y 1 0 0 0 −x·x′ −y·x′] · h = x′
[0 0 0 x y 1 −x·y′ −y·y′] · h = y′

Four correspondences determine H exactly; with clicked points (which are off by a pixel or two) I use 13–15 well-spread pairs per image pair and solve the overdetermined 2n × 8 system A h = b by least squares (np.linalg.lstsq). Before solving, both point sets are normalized (Hartley: centroid at the origin, mean distance √2), and H is mapped back afterwards. This does not change the answer for exact data, but it keeps the columns of A on comparable scales, so the solve is much less sensitive to click noise than with raw pixel coordinates, whose products x·x′ reach 106.

I clicked the points with a small matplotlib tool (pick_points.py) on sharp corners — window corners, roof edges, sign corners, pole tops — spread over the whole overlap. The reprojection error ‖H(p) − p′‖ tells whether a click is wrong: in set 1 one pair on the base of a nearby lamp post had a much larger error than the rest, because the lamp is much closer to the camera than the building (see the parallax discussion in A.4), so I removed it.

def homography_system(im1_pts, im2_pts):
    x, y, xp, yp = im1_pts[:, 0], im1_pts[:, 1], im2_pts[:, 0], im2_pts[:, 1]
    zeros, ones = np.zeros_like(x), np.ones_like(x)
    A = np.empty((2 * len(x), 8))
    A[0::2] = np.stack([x, y, ones, zeros, zeros, zeros, -x * xp, -y * xp], axis=1)
    A[1::2] = np.stack([zeros, zeros, zeros, x, y, ones, -x * yp, -y * yp], axis=1)
    b = np.empty(2 * len(x)); b[0::2], b[1::2] = xp, yp
    return A, b

def computeH(im1_pts, im2_pts):
    T1, T2 = _normalizing_transform(im1_pts), _normalizing_transform(im2_pts)
    A, b = homography_system(apply_homography(T1, im1_pts), apply_homography(T2, im2_pts))
    h, *_ = np.linalg.lstsq(A, b, rcond=None)
    H = np.linalg.inv(T2) @ np.append(h, 1.0).reshape(3, 3) @ T1
    return H / H[2, 2]

PART A · 3

Warping and rectification

Inverse warping. Forward warping (pushing every source pixel through H) leaves holes, so both warps work backwards. I first push the four corners of the source through H to get the output bounding box. Then, for every output pixel (x′, y′) in that box, I compute its source position p = H−1(x′, y′, 1)ᵀ, divide by the third coordinate, and sample the source image there. The whole grid is processed with array operations, 256 output rows at a time to bound memory. Each warp also returns an alpha mask that is 1 where the source position lies inside the source image (and in front of the camera, i.e. the homogeneous coordinate is positive) and 0 elsewhere; A.4 uses these masks for blending.

Two samplers. warpImageNearestNeighbor rounds the source position to the nearest pixel center and copies that pixel. warpImageBilinear takes the four surrounding pixels and averages them with weights (1 − ax)(1 − ay), ax(1 − ay), (1 − ax)ay and axay, where ax, ay are the fractional parts of the source position. Both are written from scratch with NumPy; no library warp or interpolation function is used.

def _source_coords(H_inv, bbox, row_start, row_stop):
    xmin, ymin, xmax, _ = bbox
    gx, gy = np.meshgrid(np.arange(xmin, xmax + 1.0), np.arange(ymin + row_start, ymin + row_stop, dtype=float))
    den = H_inv[2, 0] * gx + H_inv[2, 1] * gy + H_inv[2, 2]
    front = den > 1e-12                      # points mapped from behind the camera are invalid
    den = np.where(front, den, 1.0)
    sx = (H_inv[0, 0] * gx + H_inv[0, 1] * gy + H_inv[0, 2]) / den
    sy = (H_inv[1, 0] * gx + H_inv[1, 1] * gy + H_inv[1, 2]) / den
    return sx, sy, front

def _sample_nearest(im, sx, sy, front):
    h, w = im.shape[:2]
    xi, yi = np.floor(sx + 0.5).astype(int), np.floor(sy + 0.5).astype(int)
    valid = front & (xi >= 0) & (xi < w) & (yi >= 0) & (yi < h)
    return im[np.clip(yi, 0, h - 1), np.clip(xi, 0, w - 1)] * valid[..., None], valid.astype(float)

def _sample_bilinear(im, sx, sy, front):
    h, w = im.shape[:2]
    valid = front & (sx >= 0) & (sx <= w - 1) & (sy >= 0) & (sy <= h - 1)
    x0 = np.clip(np.floor(sx).astype(int), 0, w - 2); y0 = np.clip(np.floor(sy).astype(int), 0, h - 2)
    ax = np.clip(sx - x0, 0, 1)[..., None];         ay = np.clip(sy - y0, 0, 1)[..., None]
    top = im[y0, x0] * (1 - ax) + im[y0, x0 + 1] * ax
    bottom = im[y0 + 1, x0] * (1 - ax) + im[y0 + 1, x0 + 1] * ax
    return (top * (1 - ay) + bottom * ay) * valid[..., None], valid.astype(float)

Rectification. To test the warps, I make a slanted rectangle look fronto-parallel. I click its four corners (top-left, top-right, bottom-right, bottom-left) and map them to an axis-aligned rectangle. With exactly four points the system is 8 × 8 and solved exactly (reprojection error 0). The rectangle's width is the average of the top and bottom edge lengths. Its height depends on what I know about the object. The recycling poster is a tall portrait poster, about 1.2 times taller than a letter sheet (8.5 × 11) of the same width. That gives a width-to-height ratio of about 0.64, so its height is width / 0.64. Averaging the left and right edges instead would give 0.92, because looking down at the sign foreshortens its vertical edges. That height would be about 30% too short, and the recycling symbol and the text would come out squashed. The PSR sign is a long landscape panel, with a width-to-height ratio of about 1.8, so its height is width / 1.8. Averaging its edges would give only 1.11, because the sign recedes steeply to the right, and the letters would come out visibly condensed. Everything off the sign's plane (trees, grass, posts) is stretched, as expected, because the homography is only correct for that plane.

The rectified images are stored at full resolution; click one to open it and zoom in. At this size the two look alike, and the difference is in the pixels (below).

Nearest neighbor vs. bilinear. Below are 110 × 110 px crops of each rectified sign, enlarged 4× with pixel replication so single pixels are visible. Each crop is taken where the sign has the most edges. The rectification enlarges the far side of each sign, so one source pixel is spread over several output pixels. Nearest neighbor copies whole source pixels, so slanted strokes become staircases (the “W” of “We”, the serifs, the edges of “GREEN”) and thin strokes change thickness from letter to letter. Bilinear interpolation varies smoothly between source pixels, so edges stay straight and anti-aliased. Its result is slightly softer, but it never invents structure.

Speed. Bilinear is about 3× slower. It gathers four source pixels per output pixel instead of one and does three weighted blends per channel. Nearest neighbor does one gather. Both are fast enough here, but I use bilinear for all mosaics because the quality difference is visible and the extra cost is well under a second per photo.

PART A · 4

Blending images into a mosaic

Procedure.

  1. Reference frame. The middle photo is the reference (for two-photo sets, the right one), so the distortion is spread over both sides instead of piling up at one end.
  2. Chain the homographies. I only click neighboring pairs, which gives Hi from photo i to photo i + 1. The map from any photo to the reference is a product of these: H1→2 for the left photo and H2→3−1 for the right one.
  3. Shared canvas. The four corners of every photo are pushed through its map to the reference. The union of the resulting boxes is the canvas, so nothing is cut off.
  4. Warp. Every photo is inverse-warped onto the full canvas with warpImageBilinear, together with its alpha mask.
  5. Blend. The overlaps are combined with one of three methods, compared below.
  • Overwrite (baseline): each photo is pasted over the previous one. Any exposure difference shows up as a hard seam.
  • Feathering (weighted average): each photo's weight is the distance transform of its alpha mask, normalized to 1 at its center and falling linearly to 0 at its border. The output is Σ wiIi / Σ wi, so photos fade smoothly into each other.
  • Two-band blending (a 2-level Laplacian pyramid): each photo is split into a low band (Gaussian blur, σ = 3 px, computed only inside its mask so the black border does not bleed in) and a high band (photo minus low band). The low bands are feathered as above, which hides exposure differences. Each output pixel takes its high band from the photo with the largest weight there, so fine detail is never averaged.

Seams. Exposure and lens vignetting differ slightly between shots, so the same sky is a slightly different blue in each photo. Overwrite turns this into hard vertical edges in the sky and on the lawn. The base of the lamp post is also cut in two, because the lamp is close to the camera (the same parallax as in set 3 below). Blending the low frequencies spreads the exposure change over the whole overlap, where it is invisible.

Why two bands. Feathering fixes the seams of the overwrite result, but wherever the photos disagree slightly it averages two copies of an edge. This happens with leaves moving in the wind, or with a residual misalignment of a pixel or two, and the result is a soft double image (ghosting). The crops below are taken where feathering differs most from the two-band result. In both sets this lands on trees, whose leaves moved between the shots. Two-band blending keeps one copy of the fine detail and blends only the smooth colors.

What went wrong in set 3: parallax

Set 3 has an RMS error of 4.07 px, three to four times that of the other sets, although each click was checked. The errors are not random. When I fit H to subsets of the points, the points on the distant houses, poles and traffic light agree with each other, and the points on the ground at my feet and on the nearby pedestrian signal agree with each other, but the two groups disagree. That is the signature of parallax: between the two shots my phone also moved slightly instead of only rotating about its lens. A homography is exact for a pure rotation, or for a single plane, but with a translated camera points at different depths shift by different amounts, and no single H can fit them all.

The table compares the fit to all 13 points with a fit to only the 7 far points. The far-only H fits the background almost perfectly (1.2 px), but it is up to 24 px off on the ground. In the mosaic, the crosswalk stripes, the yellow tactile pad and the person's legs then appear twice. The all-points fit splits the difference, at most 6.4 px anywhere, which the two-band blend hides well. So I kept all 13 points. The real fix is to retake the photos while turning the phone strictly about its lens.

PART B

Feature Matching for Autostitching

PART B · 1

Harris corners and ANMS

Part B replaces my clicking with the method of Brown, Szeliski and Winder (“Multi-Image Matching using Multi-Scale Oriented Patches”), with the course's simplifications: one scale, no sub-pixel refinement and no rotation invariance. Everything runs on the same photos and the same working size (at most 1600 px) as Part A.

Harris corners. At every pixel, the structure tensor M is built from Sobel gradients and smoothed with a Gaussian of σ = 1. The corner strength is f = 2 det(M) / (tr(M) + ε). This is the same formula as the course's harris.py; I compute it with scipy.ndimage because that file needs scikit-image. A corner is a 3 × 3 local maximum of f that lies more than 20 px from the border, so its descriptor window fits. It must also reach at least 10−3 of the strongest response, which removes noise “corners” in flat sky. That leaves 28,212–35,856 corners per photo, on nearly every textured surface: far too many to match.

Adaptive non-maximal suppression. Taking just the strongest corners would cluster them where the contrast is highest, and the overlap between two photos may have few of those. ANMS instead gives each corner a suppression radius, the distance to the nearest corner that is clearly stronger:

ri = minj ‖xi − xj‖  subject to  f(xi) < crobust f(xj),   crobust = 0.9

I keep the 500 corners with the largest radii, the number used in the paper. These are the corners that dominate their neighborhood, so they spread over the whole photo: the smallest kept radius is 34–38 px. Once the corners are sorted by strength, the ones clearly stronger than corner i are a prefix of the list, so each radius is one distance computation against that prefix. Corners, ANMS and descriptors together take 4–6 s per photo.

def anms(xy, strength, n_points=500, c_robust=0.9):
    order = np.argsort(-strength)
    ranked_xy, ranked = xy[order], strength[order]
    # in descending order, the corners clearly stronger than corner i are a prefix of the list
    stronger = np.searchsorted(-ranked, -ranked / c_robust, side="left")
    radius2 = np.full(len(ranked), np.inf)
    for i in np.nonzero(stronger)[0]:
        radius2[i] = ((ranked_xy[:stronger[i]] - ranked_xy[i]) ** 2).sum(axis=1).min()
    keep = np.argsort(-radius2, kind="stable")[:n_points]
    return order[keep], np.sqrt(radius2[keep])

PART B · 2

Feature descriptors

Each kept corner gets an axis-aligned 8 × 8 descriptor sampled from the 40 × 40 window around it. I blur the grayscale photo with a Gaussian of σ = 2.5 and take one sample every 5 px, which avoids aliasing. The result is low-frequency on purpose: a corner found a pixel or two away from the true position still gives almost the same descriptor. Each patch is then bias/gain normalized, d′ = (d − μ) / σ, so a brightness or contrast change between shots does not affect it. As the course allows, there is no rotation invariance and no wavelet step.

def extract_descriptors(gray, xy):
    blurred = gaussian_filter(gray, 2.5)
    offsets = 5 * np.arange(8) - 20 + 2                # -18, -13, ..., 17: one sample per 5 x 5 cell of the 40 x 40 window
    cols = xy[:, 0].astype(int)[:, None] + offsets
    rows = xy[:, 1].astype(int)[:, None] + offsets
    patches = blurred[rows[:, :, None], cols[:, None, :]]
    mean, std = patches.mean(axis=(1, 2), keepdims=True), patches.std(axis=(1, 2), keepdims=True)
    return (patches - mean) / np.maximum(std, 1e-8)

PART B · 3

Feature matching

For every descriptor in one photo I compute the squared error to all 500 descriptors in the other. The size of the best error says little about whether a match is right, so I use Lowe's test instead: the ratio e1-NN / e2-NN between the best and second-best error. A correct match is much better than any alternative, while a wrong one is about as good as the runner-up. If several features pick the same target, only the one with the lowest ratio survives.

I use a threshold of 0.6. In Figure 6b of the paper, the distributions for correct and incorrect matches cross near 0.65 on this same squared-error ratio. My own data supports the choice: the table counts, over all six photo pairs, the nearest neighbors below each ratio and how many of them land within 3 px of where the final H sends them. Raising the threshold from 0.6 to 0.9 nearly doubles the matches but adds few consistent ones.

PART B · 4

RANSAC and automatic mosaics

4-point RANSAC. Some ratio-test matches still disagree with the main homography, and a single one would ruin a least-squares fit. So I repeat this 5,000 times: pick 4 random matches, compute the exact homography through them with computeH, and count the matches it maps to within 2 px of their partners. The largest such set wins. I then refit H by least squares on that whole set and recollect the inliers until they stop changing. The random seed is fixed, so the result is reproducible.

A random sample of 4 is all inliers with probability w4, where w is the inlier rate. My lowest rate is 40%, so about 180 iterations already give a 99% chance of one clean sample. 5,000 iterations leave a wide margin and take about 0.5 s per pair. The mosaics then use exactly the Part A code: chained homographies, the middle photo as reference, bilinear warping and two-band blending.

def ransac_homography(pts1, pts2, threshold=2.0, iterations=5000, seed=180):
    rng = np.random.default_rng(seed)
    best = np.zeros(len(pts1), dtype=bool)
    for _ in range(iterations):
        sample = rng.choice(len(pts1), 4, replace=False)
        inliers = reprojection_error(computeH(pts1[sample], pts2[sample]), pts1, pts2) < threshold
        if inliers.sum() > best.sum():
            best = inliers
    for _ in range(10):                                # refit on all inliers until the set stops changing
        H = computeH(pts1[best], pts2[best])
        inliers = reprojection_error(H, pts1, pts2) < threshold
        if (inliers == best).all() or inliers.sum() < 4:
            break
        best = inliers
    return H, best

What RANSAC rejects is mostly not wrong

In the figures above, the rejected matches are not scattered at random. In set 1 almost the whole lawn and path is red, although those matches look correct. To test this, I ran RANSAC a second time on just the rejected matches. In every pair it finds another 29–42 matches that agree with each other on a single homography, 5–12 px away from the first one.

So the photos hold two depth layers, typically the building or background and the ground near the camera. This is the parallax from Part A again: the phone moved slightly between shots instead of rotating only about its lens. It affects all four sets, not only set 3, where it was just most visible in the clicks. RANSAC locks onto whichever layer has the most matches. That is the building or far scene in sets 1, 2 and 4, and the ground in set 3, which explains why set 3 has the largest error on my clicks: they cover both layers.

Manual vs. automatic

Both columns use the same photos and blending; only the homographies differ. In sets 1, 2 and 4 I see no visible misalignment in either version, even though the automatic ones took no clicking.

Set 3 is the one place where the two differ visibly, because they treat the two depth layers differently. RANSAC fits the ground, so the crosswalk is aligned, but the distant pole and palm get a faint halo. My clicked points cover both layers, so the manual H spreads the error and keeps the pole and palm cleaner. The faint dark disc on the crosswalk is the car that drove through between the two shots; it appears in both, because no homography can fix a moving object.
